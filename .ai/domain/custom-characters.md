# Domain: Custom characters (player-made fighters)

A player can make their own fighter from a **pose sheet** they generated with an image AI (from the prompt of the character type they picked — see "The prompt"). Nothing calls an AI from the server: the player does that step, and the app validates and converts the result. The sheet is built into a **draft** the player previews; only when they use it does it become their equipped fighter, which everyone then sees on the battlefield.

Two places: the `/character` page (`CustomCharacterController`) is the **prompt guide only** (pick a type, copy the prompt, the requirements) with a section on using the same sheet for custom minions (Character → Minions tab, Use my fighter, up to 3 custom minions in a pool with the five defaults) and same-tab links to `/battlefield/open/editor` and `/battlefield/open/minions` (the latter also flashes `editor_tab`, which reaches the Character tab's `characterTabs` Alpine component (`sheet/index.js`) as `open-custom-editor {tab}` or, if it mounts later, as `window.__openCustomEditor = 'minions'`, and opens Character → Minions). It flashes the request once and redirects to the clean `/battlefield`, so a reload never reopens the sheet. Older `/battlefield?sheet=character&editor=1` links redirect through the same route. The link waits for `battlefield-ready` (at most `READY_CEILING_MS`) before opening the Character tab and editor. The editor (`Livewire\CustomCharacterEditor`) sits beside the shared show stage in Forge mode and below it at narrow widths. Everything a player does while the battlefield is open belongs to the game world (`.ai/design/README.md`).

## The flow

1. **Build.** `StageCustomCharacter` (under the player's lock) converts the sheet and writes the strips to the **staged** area; a `custom_character_drafts` row (one per user) points at them. The live fighter is untouched, nothing is broadcast.
2. **Preview.** The editor shows the draft on the sheet's own show stage (scale 4) marked *Previewing*, with the move hotbar, play/pause and frame stepping at the game's frame rates, and *Use this fighter* / *Discard preview*.
3. **Confirm.** `ConfirmCustomCharacter` is bound to the hash the player previewed and to the player: a draft replaced in another tab, or someone else's, is never confirmed (`CustomCharacterDraftMissingException`), and confirming the version already in use is a harmless no-op. It moves the files from staged to confirmed, then in one transaction turns the old `current` row into `previous`, makes the new version the `current` row (name and `enabled` carried over from the old one, or the default name for a first fighter; a `previous` row with the same hash is promoted instead of duplicated), trims the history to `max_versions` (current + previous, oldest first, never `current`) and deletes the draft; files of dropped versions are deleted only after the transaction. It then broadcasts `FighterCharacterChanged`.
4. **Manage.** Rename (`RenameCustomCharacter`: control, invisible and bidi-override characters stripped, trimmed, cut to `name_max`, empty → `default_name`), switch to an earlier version (`EquipCustomCharacterVersion`, also equips and broadcasts), delete an earlier version (`DeleteCustomCharacterVersion`; the one in use is refused), remove the fighter (`RemoveCustomCharacter`).
5. **Remove.** In one transaction deletes every fighter row of the player (current, previous, draft), then every file, all under the player's lock; then broadcasts so every client drops the fighter live. The player falls back to the roster character they had equipped (`users.equipped_character` is never touched here). Who may: the owner, or a role holding `Delete:CustomCharacter` (`CustomCharacterPolicy`). The admin list uses `ViewAny:CustomCharacter`; Rename needs `Update:CustomCharacter`, calls the same locked rename service as the player and broadcasts the change. Deleting a user clears their files (`User::booted`).

Equipping a roster character in the sheet turns the custom fighter off (`active` false, the `enabled` column) without deleting it, and equipping the Custom slot turns it back on (`FighterSheet::equip('custom')`). `User::equippedFighterKey()` is `custom` while it is on, else the roster key; `User::customFighterState()` is null while it is off.

## Data

One table, `custom_sprites`, holds every custom sprite of both kinds (fighter and minion). Each row is one version of one sprite:

| Column | Meaning |
|---|---|
| `user_id` | Owner (FK `users`, cascade on delete) |
| `type` | `fighter` or `minion` (`CustomSpriteType`) |
| `state` | `draft` (built, not yet used), `current` (in use), `previous` (history; fighters only) (`CustomSpriteState`) |
| `slot` | Minion slot `1..minions_max` for `minion/current`, else null |
| `version_hash` | Hash of the strips' PNG content |
| `enabled` | Fighter: equipped (`active`). Minion: ticked into the pool |
| `data` | JSON: `name`, `animations`, and for a minion `body_px`, `source` (`upload` or `fighter`) |

Unique indexes (partial, the same SQL on Postgres and SQLite): `(user_id, type, slot) WHERE state = 'current'`, `(user_id, type) WHERE state = 'draft'`, `(user_id, type, version_hash) WHERE state <> 'draft'`; plus a plain `(user_id, type, state)`.

The old class names stay as thin views on that table (a global scope on `type` + `state`, `type`/`state` filled on `creating`, accessors for the `data` keys), so the fighter services and the Shield permission names (`*:CustomCharacter`) did not change:

| Class | Rows |
|---|---|
| `CustomCharacter` | fighter / current (`active` is the `enabled` column) |
| `CustomCharacterVersion` | fighter / current + previous (`CustomCharacter::versions()`) |
| `CustomCharacterDraft` | fighter / draft |
| `CustomMinion` | minion / current |
| `CustomMinionDraft` | minion / draft |

Query-builder calls (`where`, `update`, `pluck`, `orderBy`) must use real columns (`enabled`, `slot`, ...), never `data->...`: a mass update bypasses the accessors. The migration `2026_10_25_000001_create_custom_sprites_table` copies the three old fighter tables (and the staging-only minion tables when they exist) and drops them; its `down()` rebuilds the three fighter tables (a version row equal to the in-use version takes its `created_at` from the `current` row). `users` gained `minion_defaults_off` (json) and `minion_pool_rev` (int).

## The sheet contract

Enforced in code, in this order, and a violation throws `InvalidPoseSheetException` carrying a `PoseSheetProblem` (user-facing message; nothing is stored):

| Check | Class | Rule |
|---|---|---|
| File | `PoseSheetDecoder` | PNG/JPEG/WebP; ≤ `max_bytes` (4 MB); sides `min_side`..`max_side` (512..2048); ≤ `max_pixels` (4,194,304), all read from the header before decoding |
| Background | `PoseSheetKeyer` | solid `#FF00FF` or transparent, recognised from the border; magenta is eroded 1 px to drop tinted edge pixels |
| Layout | `PoseSheetLocator` | rows and poses found from empty gaps; row count and per-row pose counts from `custom_character.rows` (idle 2–4, walk 4, attack 3, death 3). A pose is a run of columns with ink; poses are split only by empty columns (≥ 0.5% of the width), so anything that bridges two poses — a magic circle, a bolt, a swirl, a long cape or braid — merges them and the row count comes out short (a wizard sheet whose spell circle touched the next pose gave "attack has 2, expected 3"). The prompt therefore lets the AI draw effects and projectiles but requires them (and every pose) to stay inside their own cell with ≥ 5% of the sheet width of clear space to the next pose, and the error hint says touching poses count as one |
| Stray marks | `StrayMarkRemover` | detached blobs under `stray_ratio` of a pose's ink (motion lines, sparks) are erased; a larger detached part (a dropped sword) is kept |
| Sanity | `PoseSheetValidator` | no pose touches a sheet edge; idle/walk heights within `size_tolerance` of their median; that median at least `sprite_height` (`PosesTooSmall`: poses are only ever shrunk) |

**Size limits are a memory budget.** The build runs in the request on PHP arrays that grow with the pixel count. Measured with a 256M `memory_limit` (`BuildCeilingTest`): a noisy 2048 px sheet peaks near 115 MB, a 4000 px one near 230 MB (a fatal on a busier sheet), so the ceiling is 2048 / 4.2 MP. Livewire's temporary upload limit is the same 4 MB (`config/livewire.php`).

Changing the layout or the prompt in a way that invalidates old sheets → bump `custom_character.prompt_version`.

## Conversion

`CustomCharacterBuilder::execute()` runs the chain above, then: `SpritePixelator` (one scale for every pose from the median idle/walk height → `sprite_height`; each output pixel averages only ink pixels; one shared palette of `palette_colors` via `PaletteQuantizer`, a median cut that splits the widest colour range so rare colours like pupils survive) → `RosterToneMatcher` (scales saturation/lightness toward the roster's muted look) → `SpriteOutliner` (1 px `outline_color` on the outer edge) → `SpriteStripBuilder` (100×100 frames, feet on row 58 = `FOOT_ROW`, centred by the lower body; every row plays its poses in order, idle/walk/attack each held two frames and death one (idle used to hold only the last pose and bob, which threw away the motion drawn in the other idle poses); a pose wider than 98 px or taller than the 58 rows above the foot line is shrunk to fit instead of bleeding into the next frame). Fighter frames stay **100 px** — never upscale.

Animation table it produces (frames @ rate): idle 2 frames per idle pose (4–8) @ 8, walk 8 @ 16 (a run: the sheet's second row is a fast run cycle, and the strip keeps the `walk` name the game uses for a charging fighter), attack 6 @ 12, death 3 @ 6.

## Storage

`CustomCharacterStore` owns every path and every write, on the disk named by `custom_character.disk` (`public` by default; `CustomCharacterStore::disk()` is the one place that reads it). Confirmed strips are `custom-characters/{user}/{hash}/{idle,walk,attack,death}.png`; a draft's are `custom-characters/{user}/staged/{hash}/…`, so a draft can never be mistaken for the fighter in use. The hash is of the PNG content, so a changed fighter gets a new URL (hosts cache non-hashed assets for days). The uploaded sheet is never kept.

- **Writes are checked.** A full or unwritable disk throws `CustomCharacterStorageException` (and removes what was half-written) instead of letting a row point at files that were never saved. Cleanup (prune, forget, discard) never throws: it runs after the database changed.
- **Order.** Stage writes the new files, then the draft row, then removes older staged files. Confirm promotes the files (`promote()` **copies** all four strips, checks all four are in place, and only then deletes the staged folder: a failure half way leaves the draft whole and no half-confirmed folder; a confirmed folder with only some strips is completed, not taken as done), then commits the rows, then prunes versions that left the history. Nothing is deleted before the row that stops referencing it is gone.
- **One change at a time per player.** `CustomCharacterLock` (`Cache::lock`, key `CacheKeys::customCharacterBuild`, held at most `lock_hold_seconds` (150 s), waits `lock_seconds` (10 s) then `CustomCharacterBusyException`) wraps **every** change: stage, confirm, discard, rename, equip, equip-version, delete-version and remove. The store checks its deadline between writes and copies, aborting a slow operation while its lock is still held. The rate limiter counts attempts but does not serialise them. Other players never wait. The editor and Filament actions show the busy message; the sheet's equip returns to the server's current fighter (`sheet-equip-failed`).
- **Where it is served from.** `baseUrl()` is a same-origin **path** when the disk's URL is on the app's host (the battlefield reads the strips' pixels for the heel, which a cross-origin image forbids) and the **full URL** when the disk is another host (a bucket or CDN such as the `r2` disk). In that case the host must send CORS headers: the loader and the heel probe set `crossOrigin = 'anonymous'` for `http(s)` URLs, and `stripUrl()` accepts them. Taking an image down behind an `immutable` CDN cache also needs a purge, which this app does not do.

Uploads are rate limited (`uploads_per_hour`, key `custom-character-upload:{user_id}`) because a build costs several seconds of CPU.

**Lifecycle.** A draft nobody used is removed after `draft_ttl_hours` (24) by `custom-characters:prune-drafts` (daily 04:00; `PruneStaleCustomCharacterDrafts`, per player under the lock). Cleanup failures are reported while the database change stands. `custom-characters:prune-orphans` runs daily at 04:30: under each player's lock it re-reads version and draft references, and removes only unreferenced folders at least one hour old. Missing or unreadable age keeps a folder. Changing `custom_character.disk` after fighters exist points the app at an empty place: run `custom-characters:copy-disk <from> <to>` first, then change the setting.

## The editor

`Livewire\CustomCharacterEditor` mounts lazily inside `.cce-drawer`, beside the shared stage on desktop. The draft is a real `custom-draft` roster slot, so the stage and inspector play its moves at the same size as any fighter. The upload form shows a selected-file thumbnail and dimensions, upload percentage, an indeterminate build bar, and a single actionable error with `PoseSheetProblem::hint()`. A first-time player sees the existing Lancer animation strips as a monochrome alpha silhouette for the four source-sheet rows, with battle visuals hidden; it pauses when Forge closes or reduced motion is requested. The pose counts still describe the uploaded sheet, while the shadow shows reference motion from the roster. The editor also holds the fighter name, removal action and numbered version cards; a card's Preview button peeks on the shared stage without equipping it. Remove and Delete version ask in the sheet (`$confirming`, Cancel focused, Escape cancels), never `wire:confirm`. Results use `sheet-toast`; failure announces `sheet-error` and requests `sheet-focus`. The editor dispatches `custom-character-changed` with `{custom, equipped, draft}`; `FighterSheet` provides the initial state and follows that event for later mounts. The Character stage also listens for `custom-character-state`, `custom-version-peek`, `open-custom-editor`, `sheet-escape` and own `FighterCharacterChanged` broadcasts. Alpine state lives on inner elements because the lazy component's root is morphed on mount. Avoid naming Livewire methods `upload`, `removeUpload`, `uploadMultiple` or `cancelUpload`: the browser reserves them for file upload.

## On the battlefield

While the custom fighter is equipped it wins over the equipped roster character and over the per-boss assignment. `User::characterForBoss()` is unchanged and still sends a roster key as the fallback an old client (or a failed load) shows.

**Wire shape.** `User::customFighterState()` → `CustomCharacter::broadcastState()`: `{version, url_base, animations}` — the version hash, where the strips are served from (see Storage), and the `{frames, rate}` table. It rides as `custom_character` (null for everyone else) on `FighterJoined`, `FighterCharging` (a synthetic client-side rejoin), `FighterCharacterChanged` and each `BossSpawned.fighters[]` row, as `customCharacter` (same inner shape) on each boot-payload fighter, and on `/api/state`. A client that missed a change (Reverb has no replay) catches up from the next `FighterCharging`, which carries the same state (`charge.js` hands it to `updateCharacters` for a custom fighter, or for a fighter currently showing one).

**Client.** `fighter/custom-fighter.js` (pure) reads the payload (`normalizeCustomCharacter` takes `url_base` and the snapshot's `urlBase`) and builds a FIGHTER_TYPES-shaped entry — `key` `custom-<user>-<version>`, `texture` its own, `attackType` slash, no per-attack art. `fighter/custom-fighter-loader.js` fetches the four strips, stacks them into **one canvas texture** of named 100 px frames (`<key>-idle-0` … the names the atlas uses, so the fighter code reads both alike) and registers the animations; it dedupes concurrent loads and the texture belongs to the game, so a rotate-restart and a repeat request are free. `Fighter` shows a roster fighter first and swaps the custom one in when it lands (`_requestCustomFighter`). Every `setTexture`/`add.sprite` of a body goes through `textureOf(ftype)`.

**Request state** (`fighter/custom-fighter-requests.js`, one `entry.customRequest`): every update that names a custom fighter first states what is wanted now (`want`, even when nothing needs loading), and the newest wins — a late load for any other version is dropped and its texture released if nothing shows it; a load in flight blocks a repeat of the *same* version only (a swap a hit cut short is asked for again by the next update); a failed version waits `CUSTOM_RETRY_MS` (30 s) while a *different*, newer one is not held back. The completion callbacks of an animated swap check they are still the wanted look before acting, so a newer choice made during the death → summon is never reverted by the older swap.

**Animation state.** The swap lands in whatever state the fighter is in: charging → walk (the ring and bubble stay), idle → idle, mid-attack → the type changes under the playing attack and its completion hands over to the new look (`handleHit` reads `fighter.ftype.key` at completion, not the key it started with). The look a fighter leaves is released (`releaseCustomFighter`: its texture and animations), so a long session does not collect one canvas per rebuild; a roster look is never released (shared atlas). The looks left while an attack plays are parked in `entry.releaseOnApply` (a list: two swaps can land in one attack) and let go of when that attack ends (the playing animation still draws from them), by `_releasePending`. A fighter that leaves the field withdraws its requests and, once its fade is over, releases the look it showed and any parked ones (`_releaseLeft`) unless the same player came back with one; a load that lands for a fighter who has left is released at once. A swap whose wanted look flips back while the death plays stands the old fighter up again instead of leaving it on its last death frame. The blade dash's ghosts use the look the dash began with.

**Size.** The strips are built `sprite_height` (52) px tall and the field draws them smaller: the body stands 22 px tall in the roster's pixels (the roster fighters are 18, and a custom one read as small at 18). The height is a detail budget, not a display size: an AI sheet's poses are ~200 px tall and every output pixel averages the source pixels it covers, so at 22 px the costume (armour, tunic, trim) averaged into brown and the face lost its goggles; measured on a real sheet, 32 kept the face but not the costume, 44 kept both and 52 a little more. 52 is about the ceiling: the frame is 100 px with the feet on row 58, so a taller body is squeezed back to ~58 (measured: 66 and 88 came out identical). Hence 52 built, 22 shown (`bodyScale` 22/52), with `palette_colors` 64 and `tone_saturation`/`tone_lightness` 1 (the sheet's own colours; the tone matcher stays, as a no-op, for anyone who wants a muted pull). Fighters built at an older height are drawn at the wrong size until their player rebuilds them. `customFighterType` carries `bodyScale` (`CUSTOM_STAND_PX / CUSTOM_BODY_PX` = 22/52) and `bodyOffsetY` (keeps the feet on the roster's line when scaled about the frame centre), plus `bodyPx` and `headTop` so the avatar sits above its own, taller head (`avatarCenterY(key, scale, ftype)`); `Fighter._fitBody` applies them, and puts a roster body back when a custom one is removed; the heel offset includes the nudge (`shared/heel.js`). `CUSTOM_BODY_PX`, `CUSTOM_FOOT_ROW` and `CUSTOM_FRAME` in `custom-fighter.js` copy `custom_character.sprite_height`, `SpriteStripBuilder::FOOT_ROW` and `FRAME`; `CustomCharacterConfigTest` fails if they drift.

**Snapshot.** `snapshotState()` writes `character` as the **roster** key (`entry.rosterKey`, kept from the payload's fallback — the boot payload only ever holds one) and `customCharacter` as the newest request, else the look on (`snapshotSpec`), so a rotate-restart builds the fighter from the textures already loaded, or requests them again.

Limits: an attack is always the slash animation; the roster's teammate faces still use the equipped roster character. Minions do not follow the equipped fighter: they come from the player's own minion set (see Custom minions), else the five default types.

## In the fighter sheet

The Character tab (`livewire/fighter-sheet/character.blade.php`, `sheet/character-stage.js`) leads the roster with a Create/Manage action tile (`.slot-add`). It opens Forge mode (`.char-body.forging`): the roster hides, the shared stage stays visible beside the scrollable `.cce-drawer`, and the two stack at narrow widths. With no fighter the stage hides battle visuals and shows the selectable Idle/Walk/Attack/Death motion example; upload and build phases update its visual state. Back, a fighter slot or the tile closes Forge. A confirmed fighter has its own `CUSTOM` slot and a pending build has a `DRAFT` slot; selecting the draft offers Use and Discard, while `#inspector` offers Pause, Frame and Play. `OtherCustomCharacters` adds each other player's active fighter as a separate preview slot, identified by author; it has no Equip or Edit action. `FighterSheet` seeds `$customCharacter` and `$customDraft` and refreshes them from `custom-character-changed`. `equip('custom')` turns a saved fighter on; choosing a roster fighter turns it off without deleting it.

`sheet/custom-roster.js` makes it look like a roster fighter to the sheet's sprite helpers: `registerCustomRoster` puts a roster-shaped entry (`anims` whose `file` is the served strip URL, one attack named `attack1`; `sheet-roster.js`'s `stripUrl` passes a path or `http(s)` URL through) and a fixed body box into `BY_KEY`/`BOX` under key `custom`, and removes them when the user has none, so nothing lingers from an earlier mount. `nameOf(key)` (`sprite-strip.js`) is the player's name for `custom`. The **Profile tab's mini-stage** registers it too (it mounts first), shows it while equipped, and follows the editor's events and live `CHARACTER_CHANGED` broadcasts.

The ingest path pays one indexed query per hook event for `customCharacter` (the events lazy-load it once per request and the model caches it); that is accepted rather than eager-loaded, because the eager load would cost the same query.

## Custom minions

A player can hold up to `custom_character.minions_max` (3) custom minions. They use the same pose-sheet contract, pipeline and prompt as a fighter (the nine class prompts; no minion-specific prompt). Each subagent the player dispatches summons a **random look from the player's pool**: the five default looks (`custom_character.default_minions`, the keys of `MINION_TYPES`) plus every custom minion, minus whatever the player un-ticked.

**Data.** Rows of `custom_sprites` with `type = minion`: `minion/current` (one per slot, `slot` 1..3, `enabled` = ticked; `data`: `name`, `animations`, `body_px`, `source` upload or fighter) and `minion/draft` (at most one; `slot` is the slot it will replace, null when it adds a minion; `name` is null for an upload and the fighter's name for a draft taken from the fighter). `body_px` is the measured ink height of idle frame 0 (`MeasureStripBodyHeight`: first to last row with ink, valid `1..58`; a strip with no ink is `BlankStripException`), because the field scales a minion by it: a strip built today has a body up to 52 px tall (the fighter build height, `sprite_height`) that is drawn at `MINION_SIZE_RATIO` of a roster fighter's 18 px, while a minion copied from a fighter built before the 52 px change is shorter (28 or 22 px) and needs a different scale. A new minion is named `Minion <slot>` (or the fighter's name); the name follows the slot, so Replace keeps it. There is no version history.

**Pool and ticks.** Only what the player un-ticked is stored: `users.minion_defaults_off` (list of default keys) and `enabled = false` on a minion. A player who never touched a tick has all five defaults and every minion they add; a default look added to the game later is ticked for everyone. `MinionPool::get($user)` is the one place the pool is computed, `{rev, defaults, custom}`; with nothing ticked `defaults` is the whole list, so the pool is never empty. The cap of 3 counts custom minions only; `CustomMinionSlots::firstFree()`/`isFull()` are the only cap predicates. `TickMinionLook::execute($user, 'default:<key>'|'slot:<n>', $ticked)` runs under the player's lock; a look that is not a known default or not the player's own slot is `MinionLookUnknownException` and changes nothing (no `rev` bump, no broadcast); a tick that already matches is a no-op.

**`rev`.** `users.minion_pool_rev` orders one pool against another. Every change to the pool (tick, add, replace, remove, admin remove) increments it on the owner in the same transaction as the change; discarding a draft does not. Clients drop a pool whose `rev` is not newer than the one they hold, so a `FighterCharging` that read the pool before a Remove can never bring the removed minion back.

**Storage.** `CustomMinionStore extends CustomCharacterStore` with `ROOT = 'custom-minions'`, so files live in `custom-minions/{user}/{hash}/...` and `custom-minions/{user}/staged/{hash}/...`. It is a separate root on purpose: the fighter store's `prune()`, `forget()`, `discardStaged()` and `pruneStaged()` sweep the whole `custom-characters/{user}/` folder and would delete minion files. `copyStaged()` copies a staged folder to its confirmed place; `adoptStaged()` copies a fighter's folder into the minion root's staged area (Use my fighter). A confirm copies first, commits the rows, and only then removes the staged folder, so a failed insert leaves the draft and its files intact.

**Flow.** `StageCustomMinion($user, $bytes, ?$slot)` (build → draft; `$slot` set = Replace that slot; a sheet identical to a minion in the set → `CustomMinionDuplicateException`; a full set with no slot → `CustomMinionSetFullException`), `StageMinionFromFighter($user, ?$slot)` (Use my fighter: measures then copies the fighter's strips into a draft, a copy: later fighter changes or removal do not touch it; no custom fighter → `CustomMinionNoFighterException`; the player always sees a preview before Add), `RetargetCustomMinionDraft` (aims a draft at another slot), `ConfirmCustomMinion` (returns `ConfirmedMinion` with `outcome` `Added`/`Replaced`/`AlreadyInSet`; Replace keeps slot, name and tick; a hash already in the set is a no-op that neither announces nor bumps `rev`), `DiscardCustomMinionDraft`, `RemoveCustomMinion` (caller authorizes; bumps `rev`), `AnnounceCustomMinions` (`FighterMinionsChanged` inside `rescue()`, re-reading the user so the event carries the committed `rev`). Every write runs under the owner's `CustomCharacterLock`. Building shares the upload rate limit with the fighter editor (`CacheKeys::customCharacterUpload`, `uploads_per_hour`), so a player's fighter and minion builds never overlap; ticks, Use my fighter, remove and retarget share `minion_changes_per_minute` (30, `CacheKeys::customMinionChange`) because each broadcasts the pool.

**UI.** Character → **Minions** sub-tab (the `Fighter | Minions` strip in `livewire/fighter-sheet/character.blade.php`, Alpine `characterTabs` in `sheet/index.js`): `Livewire\CustomMinionEditor` (lazy, in `.char-pane-minions`) shows the pool as cells (`MinionPoolCells`: five default cells, three slot cells, a preview cell for a draft that has no free slot), a stage with an "At field size" view (`sheet/minion-stage.js`, thumbnails `sheet/minion-thumb.js`) and the one action that fits the selected cell (Add, Replace, Remove, Discard, tick). Every button is a `wire:click` of the component, so nothing waits for a browser event to reach a lazy component. It announces `custom-minions-changed {pool, changed}` (the Profile mini stage listens) plus `sheet-toast`/`sheet-error`. The Profile tab has one link into Character; the Forge (fighter editor) has no Minions tab.

**Wire shape.** `User::minionPoolState()` → `MinionPool::get()`: `minion_pool {rev, defaults: [key], custom: [{version, url_base, animations, body_px}]}` (each custom entry is `CustomMinion::broadcastState()`). It rides as `minion_pool` on `FighterJoined`, `FighterCharging` and `FighterMinionsChanged` (`{user_id, minion_pool}`), as `minionPool` in the boot payload, as `minion_pool` on `/api/state`, and as `minionPools` (`{[userId]: pool}`) in the `battlefield-resynced` event of `Battlefield::resync()`. It is **never** on `BossSpawned` (see `broadcasting.md`: Reverb's 10,000-byte request limit; `MinionPoolWireSizeTest` measures the Pusher body of the three events). A missing `minion_pool` means "no information", not "no pool".

**Client.** See `battlefield.md` (Custom minions): texture keys `minion-<user>-<version>` (a separate namespace, so a fighter version change never releases a texture minions still draw).

**Admin.** `CustomMinionResource` (list: slot, name, ticked; Remove) is gated by its own Shield permissions `ViewAny:CustomMinion` and `Delete:CustomMinion` through `CustomMinionPolicy` (the owner may always remove their own); `*:CustomCharacter` no longer covers minions. Remove goes through `RemoveCustomMinion`, so the owner's `rev` is bumped and the battlefield told.

**Maintenance.** `custom-characters:prune-drafts`, `custom-characters:prune-orphans` and `custom-characters:copy-disk` cover both roots (`custom-characters` and `custom-minions`), each with its own reference set.

## The prompt

The page offers nine character types: eight fantasy classes (warrior, wizard, assassin, archer, healer, necromancer, alchemist, berserker) and **Custom**, last; picking one shows that type's prompt. **Custom** is for a character that is not a fantasy hero (an idol, a cartoon character): its prompt (`prompt_custom`, selected by the type's `template` => `custom`) has no class, no costume and no COSTUME ITEMS block. It asks for the retro pixel look, to keep the character's design, outfit and colours exactly as in the picture (nothing added), and the shared output layout, with a simple attack that uses only what the character already has. The picker keeps the items typed before Custom and puts them back when a class is picked again (an item the player cleared stays cleared). `config('token_slayer.custom_character')` holds the shared template (`prompt`, with `{LABEL}`, `{label}`, `{COSTUME}`, … placeholders) and the per-class wording (`types`: the six costume items body/waist/feet/cape/weapon/hat, the class `identity`, what it must not look like (`avoid`), its row-3 `attack`); `CharacterPromptBuilder::execute()` fills one prompt per type. Each prompt makes the type the authority for the costume, lists the class defaults, and leaves a **COSTUME ITEMS block empty**: the player types into a line to override that one item, and an empty line means the class default. Adding a type = one more entry in `types` (the order is the picker's) and a thumbnail. Every prompt also carries the shared **PIXEL ART STYLE** block (`prompt_pixel_style`; identical for the eight classes, and for Custom except three lines (`prompt_style_lines`: the fantasy dungeon-crawler reference, the medieval-gear line and the fantasy-RPG feel line become neutral, so a non-fantasy character is not pushed toward fantasy): chunky grid-aligned pixels, no anti-aliasing, 2–4 shades per material, dark navy/charcoal outlines, the idle and run rows in the same slightly angled view (the run cycle is never a strict side profile; attack and defeated may be side-on), one unified sprite set); the template's COLORS line must not contradict it. The closing OUTPUT lines also keep every pose and what it carries inside its own cell with clear space between poses (see Layout above for why). The layout rows and the magenta background stay in the shared `prompt_output` because the converter depends on them (Custom uses the same one) because the converter depends on them; bump `prompt_version` if they change.

Each type button shows a thumbnail, `public/assets/custom-character/types/<type>.png` (128 x 128, transparent, one per key of `types` — `CustomCharacterEditorTest` fails when a type has none). The eight classes' were cut from one 3 x 3 image an image AI drew with nine costumes on a magenta background (the ninth, knight, was dropped; Custom's is a pixel silhouette with a sparkle, drawn in code, not cut): the sheet split in thirds, the magenta keyed out with the key colour taken back out of soft edges, stray pieces under the feet dropped, one scale for all nine, feet on a common line. A new type needs a thumbnail made the same way.

The picker is `resources/js/custom-character/prompt-picker.js` (Alpine `characterPrompt`; all prompts are sent with the page, no round trip). Switching type swaps the prompt but carries over the items the player already typed, via `prompt-items.js` (`readItems`/`fillItems`, which only touch the lines under the `COSTUME ITEMS (` heading, never the defaults listed above it), and scrolls the prompt into view without taking focus from the tiles. The guide section is static (`partials/custom-character-guide.blade.php`), so a build or a refusal never wipes what was typed.

## Admin

`Filament\Resources\CustomCharacters\CustomCharacterResource` (list only): player, name (search and sort through `data->name`), equipped, versions, updated. The list needs `ViewAny:CustomCharacter`, Rename needs `Update:CustomCharacter`, and Remove needs `Delete:CustomCharacter`; a busy owner gets a danger notification. Rename uses `RenameCustomCharacter` and `AnnounceCustomCharacter`, so cleaning and live updates match the player flow. The new permission migration grants all three to `super_admin`; assign them to other admin roles in Shield.

## Deploying

`php artisan migrate` creates `custom_sprites` (copying the old fighter tables, then dropping them), the two `users` pool columns, `ViewAny:CustomMinion`, `Delete:CustomMinion`, `Update:CustomCharacter` and grants the complete fighter permission set to `super_admin`. Assign any other admin role in Shield; a role that managed minions through the `*:CustomCharacter` permissions needs the two minion permissions. If strips move to R2, copy first (`custom-characters:copy-disk public r2`), then set `TOKEN_SLAYER_CUSTOM_CHARACTER_DISK=r2` and configure bucket CORS (`Access-Control-Allow-Origin`, `Vary: Origin`). Post-deploy check should return no rows (a player with none or several in-use fighters): `SELECT user_id FROM custom_sprites WHERE type = 'fighter' AND state = 'current' GROUP BY user_id HAVING COUNT(*) <> 1`. Compare the fighter, version and draft counts before and after the migration.

**Author.** `CustomCharacter::sheetState()` carries `author` (the owner's `displayHandle()`); `broadcastState()` never does. The stage shows it as "Created by …" on `#show-author`, set as text.
