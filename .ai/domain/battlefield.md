# Domain: Battlefield (Phaser renderer)

The deep operational guide is the `battlefield` skill (`.claude/skills/battlefield/SKILL.md`) — activate it for any work under `resources/js/battlefield/`. This file records the invariants that outlive any single change.

## Invariants

1. **Snapshot round-trip.** `snapshotState()` output must stay shape-compatible with the `data-battlefield-state` boot payload (built in `resources/views/livewire/battlefield.blade.php` from `App\Livewire\Battlefield`; shape in the `battlefield` skill). On an orientation flip `index.js`'s `applyModeChange` snapshots the scene, resizes the same `Phaser.Game`, and `scene.restart()`s it with the snapshot as `initialState` — `create()` runs again from scratch, so any state not captured in the snapshot is silently lost on rotate.
2. **Teardown symmetry.** Everything created via `scene.add.*`, tweens, timers, and `bus.on` must be released in `shutdown`. Leaks only surface after long sessions.
3. **Sprite sheets.** Fighter sheets are `frameWidth: 100`. Never upscale (a Real-ESRGAN attempt produced broken 19200×3200 sheets). Boss sheets carry their own per-type frame data in `resources/js/battlefield/config/bosses.js`.
4. **Boss cycle.** `Boss.bossTypeFor(number)` = `BOSS_TYPES[number % BOSS_TYPES.length]` — reordering or inserting into `BOSS_TYPES` changes which visual each boss number gets (including the one currently up), nothing else — the server knows only the boss `number`.
5. **Key discipline.** Fighters/charges are keyed by `user_id` from broadcast payloads — keep key types consistent (number vs string never collide-match).
6. **Layout.** Two separate logical spaces: landscape 960×540, portrait 540×960. Positions that cross the wire are normalized fractions of the sender's logical space; receiver-side clamping lives in `move-geometry.js`.
7. **Fighter size depends on headcount, by design.** `fighterDisplayConfig(count, mode)` (`layout.js`) steps `displaySize` down as more fighters join (landscape: 45px ≤14, 36px ≤28, 27px beyond; portrait: 54px ≤8, 45px beyond) so a crowded roster doesn't overflow the canvas. On top of that, `damageScaleMultiplier(damage, maxHp)` adds up to another ×1.4 for a fighter whose cumulative damage share against the current boss's `maxHp` is high. A near-empty battlefield showing oversized fighters is this combination working as intended, not a bug.
8. **The fighter atlas is a build artifact.** Source strips live in `resources/assets/battlefield/fighters/` (committed); `scripts/pack-sprites.js` (run by `npm run build`/`npm run dev`/the Vitest `pack-sprites` test) packs them into `public/assets/battlefield/fighters/fighters-atlas.{png,json}` and writes `resources/js/battlefield/config/atlas-version.js` (`ATLAS_VERSION` = content hash of the atlas JSON). All three outputs are gitignored — never hand-edit or commit them. The hash is baked into the JS bundle as `?v=`, busting the host's 7-day cache on the non-hashed atlas URL. Other sprites (bosses, companions) have no generated version: bump their hand-written `?v=` on edit (`public/assets/battlefield/CLAUDE.md`).
9. **Never baseline on a mid-tween value.** Hits, moves and attacks overlap constantly (`killTweensOf` mid-flight is routine), so any value read off a sprite that another tween may be animating is transient. Long sessions surfaced two "fixed by F5" drifts from this: the boss flinch took the boss's *current* scale as its yoyo base (overlapping hits ratcheted it flat — `impact.js` now tracks its own rest scale), and `entry.pos` was overwritten from a sprite caught mid blade-dash inside the boss column (the fighter then "returned" to and planned every move from the boss — `moveOrigin` in `move-geometry.js` now guards `handleHit`, `handleFighterMoved` and click-to-move). A persistent value derived from live sprite state must go through a guard like these.
10. **Canvas size and camera zoom move together.** `renderScale` sets both the canvas pixel size and the camera zoom; any resize of the running game (orientation flip in `index.js`'s `applyModeChange`) sizes through `render-scale.js`'s `canvasSizeFor` and updates the registry's `renderScale`, or the world renders zoomed in.
11. **Roster order is a cross-stack contract.** `FIGHTER_TYPES` key order must equal the PHP `App\Enums\FighterCharacter` case order: the server assigns a character as `cases()[(user_id + boss_id) % count]` and broadcasts the key. Locked by `tests/js/config.test.js` and `tests/Unit/FighterCharacterTest.php` — append new types at the end of both, or every existing player's assigned character shifts.

## Companions

Ambient actors are neither a **fighter** (player-controlled, keyed by `user_id`) nor a **boss** (the thing being fought, cycled by `Boss.bossTypeFor`) — they exist purely to dress the fight and never affect real HP/damage math, which always lands on the boss regardless of which branch below fires:

- **Necromancer.** A permanent fixture (present regardless of which boss is up) that performs the "join" ceremony: teleports beside a newly-joined fighter, casts, and the fighter visibly rises into existence there. Since it's one shared sprite, summons are queued one at a time; once `SUMMON_QUEUE_BURST_LIMIT` summons are already waiting (e.g. a whole team starting sessions at once), a further join skips the ceremony and reveals immediately rather than growing the wait.
- **Priest's heal flourish.** Cosmetic-only branch on Priest's attack, decided purely by the damage number's parity: even damage plays the normal elemental burst on the boss; odd damage instead shows the hit "healing" the Necromancer, which then itself visibly bolts the boss — standing in for the hit landing. The real damage/HP always applies the same way regardless of which branch plays.
- **BatSwarm.** Five bats spawn fresh alongside each boss fight (destroyed and respawned per boss, never carried over) and die off in a fixed order as boss HP crosses 80/60/40/20/10% of its max — thresholds, not a countdown, so a scene reboot mid-fight (orientation change) can re-derive which bats are alive from the current HP alone, no separate snapshot needed. A hit's visual target (a specific bat, or the boss itself) is chosen cosmetically from the damage number's last digit; a bat whose threshold this hit actually crossed always dies and takes the hit visually, overriding whatever the last digit alone would have picked.
- **Minions** (`minions.js`). Unlike the other three, scoped **per-fighter**, not per-boss-fight: each fighter's small swarm visualizes how many subagents (Claude Code Task/Agent dispatches — see below) that developer currently has running, driven by `FighterAgentCountChanged {user_id, count, seq}` (see `.ai/domain/token-tracking.md`'s Subagent dispatch tracking section for the PHP-side presence tracking). Randomly one of `MINION_TYPES` (`demon-a` / `blood-monster-a` / `smw-goomba` / `smw-babybowser` / `smw-bowser`) per spawn; capped at `MINION_MAX_VISIBLE` regardless of the real count, so a burst of parallel subagent dispatches never clutters the view. Cosmetic-only, but **is** carried through both boot paths as of this feature — `Battlefield::mount()` seeds each fighter's `agentCount` from `SubagentCountCache::many()` into the `data-battlefield-state` payload, and `snapshotState()` (`snapshot.js`) captures the live count off `scene.minions.byUser` the same way it already does for `charging`, so neither a full page reload nor an orientation-change reboot silently drops a fighter's real, still-running subagent swarm back to 0 — a gap `battlefield-reviewer` caught before ship (the boot-payload seed had been added without the matching `snapshotState()` capture). Only the swarm's own *positions/animation state* (which minion is mid-summon, its wander offset, etc.) reset on reboot, same as everything else re-derived fresh in `create()`.
  - **Independent world-space sprites, not container children.** A container child moves in perfect lockstep with its parent (zero lag) — that can't produce a trailing-behind effect when the fighter itself moves, so minions are plain scene sprites instead, repositioned every frame from `scene.js`'s `update()` (the same "companion synced to the fighter's live position each frame" pattern the activity bubble already uses).
  - **Foot anchor.** `entry.sprite.y + entry.legH * entry.sprite.scaleX` — the same "container-local offset × the container's own live scaleX" convention `move-input.js` already uses to project `legH` into world space as the fighter grows from crowd size or damage; **not** `layout.js`'s `chargeFootY`, which turned out to be dead code with the wrong ratio — caught by `battlefield-reviewer` before ship. Minion scale is recomputed every frame the same way (`baseSize * entry.sprite.scaleX`), since a container child used to get crowd/damage growth for free and an independent world-space sprite does not.
  - **Two movement modes, switched per-fighter by its own sampled speed** (a fighter idle in world space sits at exactly 0 px/s, so any small positive threshold cleanly separates "genuinely moving" from float noise):
    - **Idle** — each minion wanders independently within its own "home slot": no other fighter near falls back to `homeSlotOffset(index, count, radius)` (`minion-layout.js`, pure/tested), evenly dividing the full circle around the foot by the fighter's *current* minion count — "chia đều space" so minions never stack on each other. One or more OTHER fighters near instead routes through the gathering-zone system below. Within its own slot/zone each minion further drifts on its own independent slow timer (reusing `bat-wander.js`'s `randomWanderPoint`, same idle-hover pattern as BatSwarm/Necromancer) — "lâu lâu chạy loanh quanh chân", decorrelated per minion, not a shared/synchronized wander.
    - **Moving** (fighter mid click-to-move) — every minion's own home-slot wander is ignored in favor of trail-follow: the fighter's own foot position is recorded into a short history buffer every frame while moving; minion *i* (0-indexed) doesn't steer toward the fighter's live position, it **replays that same recorded path** `(i+1) * FOLLOW_DELAY_MS` in the past (`sampleTrail`/`minion-trail.js`, pure/tested). Because it's a true replay, the whole chain automatically bends around a click-to-move route's detours (e.g. around the HP-bar column) for free — no path geometry needed in `minions.js` itself.
  - **Front/back depth sort, pinned to front while spawning.** While `summoning` (the whole ground-circle + rise-in ceremony), a minion is forced to `MINION_DEPTH_FRONT` (above the fighter's own depth) so it always reads clearly, never hidden behind the character body. Once settled, depth switches every frame between `MINION_DEPTH_FRONT` and `MINION_DEPTH_BACK` based on `isInFrontOfFighter(point.y, foot.y)` (`minion-layout.js`, pure/tested) — a minion at or below the foot anchor draws in front of the fighter, one above it (toward leg/torso height, since minions orbit the foot in a full circle, not just its southern half) tucks behind, as if occluded by the body. Same near/far Y-sort convention the fighter's own flair-ring orbit already uses (`fighter/index.js`'s `back = sinA < 0`).
  - **Summon effect on spawn.** A scaled-down replay of the fighter-join ceremony — `Necromancer#spawnSummonCircle(x, y, scale)` (ground circle, now takes an optional smaller scale for this) plus a golden `preFX.addGlow` and a rise-in (scale 0→final, y offset→final) — without the Necromancer sprite itself performing it, since a whole swarm of them teleporting in would be visual noise; "giống lúc triệu hồi, chỉ là không có thần chết".
  - **Per-type size and attack roster (`config/companions.js`).** Each `MINION_TYPES` entry carries `charHeight` (its ink height in its own frame), `attacks` (`{anim, hitFrame, travel?, fidget?}`) and `reaction` (`{anim, holdMs?, getUp?}`). `_minionScale(entry, charHeight)` divides by the type's own `charHeight`, so the three `smw-*` types can ship at any resolution yet render at the same visual height as the 100px pair. They are currently shrunk to a height between their source's native one and the old 20px (frames 110/125/145 px, `charHeight` 22/25/29 — native 24/30/38 read as too sharp next to the chunky fighters) with a palette-snapping shrink, not the smooth downscale of the first 2026-09-24 repack that baked in blur; the native set and the converter are kept locally in `docs/sprite-work/_native-backup/`. Everything sized from "the minion's visual height" (badge, tool ring, clash bursts) goes through `BASE_CHAR_HEIGHT` (20) instead, so it stays consistent across types. Every strip is drawn facing RIGHT.
  - **Idle fidget.** A minion sampled below `WALK_SPEED_THRESHOLD_PX_PER_S` is "settled" and eligible for a periodic one-shot flourish ("khè khè / múa múa"): one of its own `attacks` picked at random, played in place — excluding `fidget: false` ones (Bowser's dash has no reason to run anywhere without a target). Cosmetic only, never for damage. Skipped and rescheduled if the minion is mid-Walk or mid-fight when its fidget timer fires. A minion settled in a gathering zone faces along the zone's direction (`flipToFaceAngle`, toward the other swarm) rather than keeping whatever way it last walked — otherwise one that just walked home from a fight kept its back to the enemy and its next fidget read as attacking backwards (caught live 2026-09-26).
  - **Idle-pruned subagents re-summon themselves for free.** Minion count now comes from `SubagentCountCache`'s Redis presence keys, each carrying its own TTL (see `.ai/domain/token-tracking.md`), not a plain increment/decrement counter — a subagent that goes quiet has its key expire on its own, then unexpectedly sends another event simply gets a brand-new key. The count rises again like any other spawn, so the client replays the summon ceremony with zero special-casing here.
  - **`FighterAgentCountChanged`'s `seq` guards against out-of-order delivery.** `handleAgentCountChanged` tracks the last-applied `seq` per user (`this.lastAppliedSeq`) and discards a broadcast whose `seq` is not strictly newer — near-simultaneous concurrent dispatches/claims on the server have no guaranteed wire delivery order, only a guaranteed order for when each one's own atomic write actually happened.
  - **Near-fighter gathering zones** (`minion-grouping.js`, pure/tested). Every idle frame, `computeZones(me, otherFighters)` clusters the *directions* to every other currently-active fighter within `NEAR_FIGHTER_RATIO × average-current-size` (5, narrowed from 7 — caught live 2026-09-24 as too wide, gathering was triggering between fighters that read as clearly separate on screen) (size-relative, not a fixed px value — self-scales with `fighterDisplayConfig`'s crowd-size shrink and damage growth, matching every other distance `minions.js` computes) into one zone per cluster (`clusterAngles`'s single-link cone-width rule: two directions close enough merge, far enough apart split — this alone produces every shape the feature needs, no special-casing per fighter count: two fighters → one zone facing each other; a reasonable triangle's own interior angles usually merge into one zone per fighter, oriented toward the group; fighters standing in a near-straight line put the middle one between two opposing zones instead). Each minion is assigned to one of its fighter's current zones (`_assignZones`, stable by the zone's own sorted neighbor-id combination — `_zoneKey` — so a minion keeps its zone as long as that exact neighbor combination is still the reason the zone exists, re-assigned at random only when it isn't), and fans out within it (`zoneFanOffset`, evenly spread across `ZONE_ARC_WIDTH_RAD`) so several minions sharing one zone don't stack.
  - **A zone's radius reaches toward the midpoint, not the fighter's own fixed idle radius.** `computeZones` also returns each zone's `distance` (the closest of its merged neighbors); the zone's target radius is `clamp(distance * ZONE_RADIUS_MIDPOINT_FRACTION, plainHomeRadius, plainHomeRadius * ZONE_RADIUS_MAX_RATIO)` — roughly halfway to the nearest neighbor, floored at the plain fallback radius, capped so a neighbor at the outer edge of `NEAR_FIGHTER_RATIO` doesn't pull minions absurdly far. `ZONE_RADIUS_MAX_RATIO` must stay `>= NEAR_FIGHTER_RATIO / (2 * IDLE_HOME_RADIUS_RATIO)` or the cap binds before the true midpoint in the outer slice of the near-range — verified live 2026-09-23: at the fixed idle radius alone (no distance-scaling), two fighters near enough to gather toward each other were often still too far apart for any minion to ever actually reach `FIGHT_PROXIMITY_PX`, so a whole nearby swarm could visibly "lean in" without a single clash ever triggering; the same failure mode reappeared at too-tight a cap and was caught by `battlefield-reviewer`.
  - **`homeAngle`/`homeRadius` are set straight to their current target every frame (`_setHomeTarget`), no smoothing at that level.** One assignment for every reason a target can move: the plain-fallback minion count changing, a zone's own cluster composition or distance changing, or a zone's direction continuously drifting as fighters walk. An earlier version instead exponentially smoothed each toward its target here (replacing an even earlier discrete-Phaser-tween version that only re-fired on a count change, since a zone's direction/distance changing every frame a nearby fighter walks needs a per-frame mechanism a one-shot tween can't provide) — but that per-parameter exponential smoothing moves fastest right when the gap is biggest, which read as a fast "vút" dash rather than a walk whenever a zone appeared/dissolved or a neighbor left (caught live 2026-09-24, the same underlying flaw already fixed for trail-follow's own movement-onset case — see "Movement onset..." below). Replaced with a single walk-speed cap in `update()` on the minion's actual rendered position, applied uniformly regardless of what's driving the target (trail sample or idle target) — see that bullet for the shared mechanism.
  - **Trail-follow-to-idle is decided per minion, not by a single shared fighter-level flag.** Minion `i` samples the trail `(i+1)*FOLLOW_DELAY_MS` in the past, so it keeps genuinely catching up along the real recorded path — at the same steady pace `sampleTrail` already produces — for a while *after* the fighter itself has stopped (`leader.moving` false) and its trail has stopped growing. `usesTrail = leader.moving || sampleTime < trailEndsAt` (`trailEndsAt` = the trail's own last recorded timestamp) is evaluated fresh per minion per frame; cutting every minion over to idle mode together the instant the fighter itself stops (the original shape) made a still-lagging minion's target jump straight to its new idle/zone position, reading as a sudden dash to catch up instead of a continued steady walk — caught live by the user.
  - **A minion's summon circle is dismissed early if its fighter starts moving before the clip finishes.** `Necromancer#spawnSummonCircle` plays a ~1.75s one-shot clip (7 frames @ 4fps) at a FIXED world position and self-destroys only on its own `ANIMATION_COMPLETE` — vastly longer than the whole minion spawn ceremony (`SUMMON_CIRCLE_LEAD_MS` + `SUMMON_RISE_MS`, well under half a second). If the fighter starts walking during that gap, the circle has no relationship to the minion's own subsequent trail-follow and gets left behind as a stray ring at the old spot. `minions.js` keeps the returned sprite as `minion.summonCircle` and calls `_dismissSummonCircle` (quick fade + destroy) the first frame `leader.moving` is true while it's still set — checked unconditionally per minion per frame, not gated on `summoning`, since the fighter can start moving either mid-ceremony or right after it finishes. Also torn down in `_teardownMinion` (covers both `despawnAll` and `_destroyOne`) in case a minion is removed outright while its circle is still playing. Caught live 2026-09-24: "triệu hồi xong mà user chạy... vẫn thấy hiệu ứng vòng vòng ở 1 chỗ trong khi agent con chạy mất rồi".
  - **Every minion move is a normal, constant walking pace — one rule, applied uniformly, regardless of what's driving the target.** `update()` computes wherever a minion needs to be this frame (`point`: a trail sample while following a moving fighter, or an idle target — zone or plain home slot — while settled) exactly as before, with no smoothing upstream (`_setHomeTarget` sets `homeAngle`/`homeRadius` straight to the current target, and `sampleTrail` was never smoothed). The ONE place smoothing happens is the minion's actual rendered position: its per-frame step toward `point` is capped at `max(fighterSpeed, MINION_WALK_SPEED_PX_PER_S) * dtSeconds` — never faster than the fighter's own currently-measured walking speed (idling around a stationary fighter, that's ~0, so `MINION_WALK_SPEED_PX_PER_S` alone sets the pace). This single cap replaces what used to be two separate, narrower mechanisms that each had to be caught and fixed live on the same underlying flaw: an **exponential ease** moves fastest in its very first frames (proportional to the remaining gap), which reads as a fast "vút" dash that decelerates into place rather than a walk whenever the gap is large — first caught for movement onset specifically (`sampleTrail` clamps to `history[0]`, the fighter's own foot position at the moment it started moving, for every minion at once during the first `(i+1)*FOLLOW_DELAY_MS` of a fresh move — "lúc gom lại nhanh thế... chạy như bình thường thôi đừng vút 1 cái như thế"), fixed there first with a trail-only conditional cap; then caught AGAIN for the idle-target case specifically — a zone appearing/dissolving or a neighbor leaving swings the target just as far in one frame, and `_stepHomeAngle`/`_stepHomeRadius`'s own separate exponential smoothing had the identical flaw ("chạy đến đánh nhau thì cũng chạy tốc độ thường... người khác bỏ đi thì cũng nên chạy tốc độ thường về chỗ cần về, đừng vụt 1 phát") — which is what led to unifying both into this one unconditional cap instead of maintaining two similar-but-separate fixes. In ordinary steady-state following, `point` only advances roughly `fighterSpeed * dtSeconds` per frame (sampled off the same real recorded path), so the cap rarely actually engages there and doesn't round off real corners — it only visibly smooths a target that just jumped.
  - **Each minion resyncs its own position the moment IT finishes trail-following, not once at the fighter level.** `_resyncMinionHome` recomputes `homeAngle`/`homeRadius` straight from that minion's own currently-rendered position relative to the foot, and resets `idleOffset` to zero (killing its wander tween first, then explicitly restarting `_scheduleIdleWander` since a killed-not-completed tween orphans that recursive chain) — called individually per minion, the frame its own `usesTrail` flips from true to false (tracked via a per-minion `wasTrailFollowing`). While trail-following, `homeAngle`/`homeRadius`/`idleOffset` are all frozen (trail-follow ignores them entirely), so without resyncing all three the idle branch's very first frame would glide from a stale pre-catch-up angle/radius/offset instead of from where the minion actually is — a snap the user caught live twice (the first fix only handled angle/radius **and** only at the fighter level; the leftover stale `idleOffset`, and minions still individually catching up when the fighter-level flag flipped, each independently produced their own version of the same pop).
  - **Only gather toward a neighbor that ALSO currently has minions.** `computeZones`'s neighbor list is filtered to fighters with `this.byUser.get(id)?.length > 0` — a nearby fighter with zero currently-dispatched subagents has nothing to meet or clash with, so it must never pull this fighter's own swarm off its normal all-around spread. Caught live: an empty-handed neighbor was still lopsiding the gathering toward it before this filter existed.
  - **Cross-fighter fights: one attacker, one victim, weighted by who outnumbers whom (2026-09-26).** Two minions belonging to *different* fighters that end up within `FIGHT_PROXIMITY_PX` of each other (checked pairwise every frame across every fighter's swarm) start a fight. Who attacks is decided by `minion-fight.js` (pure/tested): `countSidesNear` counts each side's own minions within `FIGHT_PROXIMITY_PX * FIGHT_AREA_RATIO` of the pair's midpoint (a third fighter's minion in the area counts for neither), `pickAttackerSide` weights the roll by those counts (3 vs 7 → 30% / 70%). The attacker faces the victim and plays a random entry of its type's `attacks`; a `travel` attack (goomba slam, bowser dash) tweens the attacker to `travelLanding` (beside the target, `TRAVEL_STOP_RATIO` × visual height short of it) between its `travel.from`..`travel.to` frames — the strip itself stays in place, the code does the moving. At `hitFrame` (`_landHit`) the victim faces the attacker and plays its `reaction`: a ~2.9s hurt strip for the smw types (its middle "in pain" wobble loops 12 frames — the user asked for longer twice: ~1.1s and then ~1.8s were still too fast to follow live), or for `demon-a`/`blood-monster-a` their Death strip (the pack also ships a Hurt strip, but the user chose Death so the hit reads bigger), held `holdMs` (2s) on the last frame and then `playReverse`d (`getUp`) so it reads as falling, lying there, getting up — never an instant pop back up (user requirement). Both participants are `pinned` (update() holds their spot / lets the travel tween drive it instead of walking them home) until `_endFightRole` releases them into `FIGHT_COOLDOWN_MS`; backstop timers (`FIGHT_RELEASE_MS`, strip length + 250ms) release them if an animation-complete never arrives, and `_teardownMinion` clears `fightTimers` on despawn. The hit moment also fires `_spawnClashVfxSequence` (kept at the user's request): `CLASH_VFX_BURST_COUNT` (3) staggered explosion bursts (`_spawnClashVfxBurst` — one of `MINION_CLASH_EFFECTS` picked at random per burst, sprite frames cropped directly out of the shared fighter atlas's `wizard-effect1`/`wizard-effect2` regions into their own standalone files, so a generic minion clash doesn't pull in the whole atlas/wizard loading path or borrow one specific fighter type's own attack visual) each with its own small fire-toned particle scatter (`TextureKey.SPARK`, the same one-shot `frequency:-1`/`.explode()` pattern `attacks/fx.js`'s `slashBurst` already uses), spread `CLASH_VFX_STAGGER_MS` apart with a small random position jitter each — reads as a sustained melee rather than one quick flash. All purely cosmetic, same never-touches-damage guarantee as the idle fidget. A minion mid-summon/mid-fidget/mid-fight/on cooldown is skipped as a fight partner.
  - **Avatar badge.** Each minion carries a small `minion.badge` image (`_positionBadge`, tucked just above its head, `MINION_BADGE_SIZE_RATIO`/`MINION_BADGE_OFFSET_RATIO`) reusing the owning fighter's OWN already-loaded avatar texture (`entry.head.texture.key` — real photo once loaded, or its generated fallback) so a viewer can tell whose subagent is whose once several fighters' swarms gather into the same zone. Read once at spawn time, not kept in sync if the fighter's real avatar finishes an async load afterward (a minion spawned in that brief window keeps the fallback look for its own lifetime) — accepted as a minor, rare cosmetic gap. Alpha/reveal timing and teardown mirror the minion sprite itself exactly (revealed in the same summon-timer callback, destroyed alongside it in both `_destroyOne` and `despawnAll`). **Must be given an explicit `setDisplaySize` at creation**, not left to the first `_positionBadge` call: the reveal fires before the rise-in tween starts (while `summoning` is still true, and `_positionBadge` only ever runs once it's false), so without an up-front small size the badge briefly showed at its native full avatar-canvas size before snapping down the instant summoning completed — caught live as "bụp 1 phát từ to hóa về bình thường".
  - **Per-agent "using a tool right now" ring (hook v7).** `FighterAgentToolUsed {user_id, agent_id, busy}` (from `PreToolUse`/`PostToolUse` fired *inside* a subagent — see `.ai/domain/token-tracking.md`) drives a pulsing cyan ring on the ONE minion sprite assigned to that `agent_id` — same visual language as `Charge.createChargingRing`, deliberately reused rather than invented ("vòng và nhấp nháy như user"). Minions are otherwise anonymous (spawn/despawn is still purely count-based, unchanged); `minion.assignedAgentId` is a lightweight layer on top: `handleAgentToolUsed` assigns an `agent_id` to the first still-`null`-assigned minion the first time it goes busy, frees it the moment that `agent_id` goes idle again. Not identity-keyed spawn/despawn — accurate for the common case (dispatched count ≤ `MINION_MAX_VISIBLE`); beyond the cap, a busy `agent_id` with nothing free to claim just gets no ring, same existing limitation the count itself already has. The ring itself (`_showToolRing`/`_positionToolRing`/`_dismissToolRing`) is `clear()`+redrawn every frame (not just repositioned) since its radius tracks the minion's own current badge size, unlike the fighter-side ring which is drawn once and left to auto-follow as a container child. A hook older than v7 never sends `agent_id` on these two events, so this stays permanently inert for that client — no error, no missing feature warning, it just never lights up.
  - **Teardown asymmetry from the old container-child design:** since nothing else owns these sprites now, `despawnAll()` (fighter leaving) must `.destroy()` each minion sprite (and its badge, its tool ring if any) itself; `destroy()` (scene shutdown) still only clears timers/tweens, since Phaser's own scene teardown destroys the display list.

## Testability

Pure logic (movement geometry, layout math, minion decisions, config shape) is extracted into plain modules and covered by Vitest in `tests/js/` (mapping and the fake-scene manager-test pattern: `resources/js/battlefield/CLAUDE.md` Testing Pattern). Rendering and feel are verified on staging.
